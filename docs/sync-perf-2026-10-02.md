# Large-vault sync performance — 2026-10-02

All data was generated. No personal vault, LAB, staging or hosted authority was used. Browser evidence used an isolated Obsidian profile, a disposable 20k-note vault and CDP. Timings are single samples under simultaneous campaign load, not a throughput SLA.

## The polling fix

`ConnectSyncController.remoteChangesWaiting()` used to clone the complete IndexedDB mirror checkpoint before requesting one change-feed event. It now uses `IndexedDbMirrorStateStore.readCheckpoint()`: a cursor, scope epoch and recovery-required boolean stored alongside the full state in **the same transaction**. Clear removes both atomically. String state keys and array summary keys cannot collide, and no database-version upgrade is required.

A full state read primes/repairs the projection once per adapter lifetime, covering state written by older plugins, stale projections after downgrades, and missing projections. Normal startup inspection already performs that read. Subsequent polls retrieve the tiny projection and verify existence with `getKey`, which does not clone documents. Injected/test state stores without this optional port retain their full-read fallback.

| --- | ---: | ---: |
| State / summary size | 43,275,829 bytes | 55 bytes |

| Slowest call | 82ms | 0.7ms |

Raw evidence: [`perf/probe-chromium-2026-10-02.json`](perf/probe-chromium-2026-10-02.json). The baseline reproduces the old read-plus-feed operation; the optimized measurement invokes the real controller with a generated IndexedDB state and an in-memory transport override.

Regression coverage includes 20 polls against 20k records with zero full-state `get` calls; recovery/uninitialized short-circuit behaviour; stale legacy summary reconciliation; atomic rollback when the summary write or delete aborts; and existing state-store failure/restart tests. At the probe commit, all 342 plugin tests and lint passed; round 4 integrated gates now pass 411 tests plus lossless qualification and lint.

The record scan takes longer overall (254ms → 485ms) because it yields to input/painting by time budget. That is deliberate. Completion, failures, auth and consent changes remain immediate; only transfer-only presentation notifications coalesce. Actual history disclosure toggles and opening one run's ledger were verified in Obsidian.

## Other guarded hotspots

- Receipt history lookup: 20k actions previously caused 200,030,000 action-id reads; indexing once bounds it to 40,000.
- Consent policy: 100 progress notifications on a 20k plan previously caused 4,040,000 command reads; immutable-preview reuse bounds it to 40,000.
- Portable path globs: a small adversarial segment/path fixture previously copied 516,133 suffix arrays. Iterative wildcard matching removes recursive explosion and call-stack growth; Unicode/classes retain semantics. 100k seeded differential cases matched the old implementation. Typical 200k matches improved ~189ms → ~92ms in Node.
- Intact large history logs no longer stringify every transfer again at startup; malformed/torn lines and pruning still trigger serialized repair. A 50k-file history regression guards that path.
- Bulk mirror echo tracking now visits each expired entry once: a 10k-write regression fell from 49,995,000 visits to ≤20k. Refreshed keys move to the tail; monotonic age preserves expiry and one-echo-only behaviour through clock changes.
- Multipart uploads reuse views of owned source-chunk tails: a 256KiB / 64-part fixture no longer copies 8,257,536 bytes of tails. Source ownership, independent request bodies and exact bytes remain protected.
- Yielded cache loading reconciles concurrent note edits/create/delete/rename. Folder-only invalidation fences both initial and incremental cache installation. Coalesced schema promises cannot republish old rules or erase a newer load.

## Integrated recheck and final evidence

Round 4 actual Obsidian recheck: cold Sync opens in 94.7ms with zero record loads; 20k record scan's largest timer gap is 26.4ms; 1,000 transfer updates cause one redraw / 16.1ms gap. Five closed-history redraws take 2.7ms with zero hidden rows. Probe recheck averages 0.101ms (100 calls, zero full reads).

A review-only trace against actual generated vault files and MemoryAuthority still finds a **180–212ms timer gap** during whole SDK review. Candidate SDK improves total time (2,868→2,079ms), but does **not** eliminate synchronous model/normalization/planning work. This comparison includes latest SDK-owner fixes plus the three perf proposals, not just the exact-document patch. No file writes, checkpoint writes or hosted requests occurred. Electron's long-task observer did not report the Node-driven stalls; timer gaps remain the meaningful responsiveness signal here.

## Remaining SDK costs and reproduction

```
npm run test:unit
node --expose-gc --loader ./test/obsidian-loader.mjs scripts/profile-large-sync.mjs 10000 20000 50000
```

The harness generates MemoryAuthority records and notes plus 50 distinct attachments. Its main review/apply cases leave attachments unselected. Separate selected-pending-file reviews hash exact bytes, stage payloads, reuse verified blobs and detect a same-size edit; they **do not apply files or use a hosted file service**. It records heap/external/RSS deltas, durable write counts/volume, paging/read counts and fake-IDB clone/probe cost. Fake IndexedDB is not a disk-latency measurement. Old inspection results are discarded between measurements instead of retaining every historical full snapshot.

The default initial fixture is **already locally populated**: it establishes the checkpoint, not an empty-vault bulk download. For safe small initial-download samples:

```
MDBASE_PROFILE_EMPTY_VAULT=1 node --expose-gc --loader ./test/obsidian-loader.mjs scripts/profile-large-sync.mjs 50 100 250
```

For three generated 32MiB files (attachment total bounded to 128MiB):

```
MDBASE_PROFILE_ATTACHMENT_COUNT=3 MDBASE_PROFILE_ATTACHMENT_BYTES=33554432 \
node --expose-gc --loader ./test/obsidian-loader.mjs scripts/profile-large-sync.mjs 20000
```

To compare a built SDK candidate, set `MDBASE_PROFILE_SDK_ROOT=/absolute/path/to/packages/sync`.

One 20k-note edit still reads the entire vault during review and again during apply, and writes roughly 216MB of full checkpoint copies across five durable writes. At 50k notes that becomes ~541MB. Do not remove durability or trust mtime/size-only caches to hide this. A tested SDK proposal reuses hashes and canonical structural proofs only after comparing freshly read exact bytes with the common authority document; its patch and evidence are in the campaign lead's `reports/perf-sdk/` directory. Journal-store adoption remains a separate, recovery-sensitive improvement. Empty-vault 50/100/250-note fixtures perform 54/104/254 writes totaling 10.3/39.5/241.6MB, despite a final 250-note checkpoint of only 539KB. Aggregate bytes grow quadratically; no 10k+ empty-vault run was attempted.

The SDK's optional append port exists, but its replay helper is not exported through `/mirror`. A third SDK proposal exports that existing helper/type, not a new persistence layout. Adoption must address ordered atomic replay/compaction, receipt history, crash tests and older writers/downgrades; blindly replaying stale phase events could undo a later paused/blocked state.
